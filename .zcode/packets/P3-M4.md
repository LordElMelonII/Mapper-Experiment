# PKG A-022 — M4 fork engine (C25/D41/D56) + the map constructors (D79)

Mission: implement `forkMap()`/`saveForkToLibrary()` per C25 with the D56 return-type amendment, and the two pure map constructors (`createWorldMap`, `duplicateMapData`) the M4 UI flows will call — the engine half of Library & forks.

Read: agents/graph-engine.md (your law).

## Context (verbatim, with IDs)

**C25 (CORE.md §5):** "Forks. Forking copies library → a chat-attached private map and switches the chat's reference to it. Forks never re-sync. Saving a fork back to the library is an explicit, non-default action (D41)."

**D41 (register):** "The user can fork a library map into a private copy attached to the chat (character-level forks later); forks stop receiving library edits. 'Save fork back to library' is an explicit action."

**D56 (register, the contract gap this packet settles):** "`forkMap`/`saveForkToLibrary` have no consumer before the fork UX lands (Phase 3 M4), and `saveForkToLibrary(): void` cannot hand the fork back to the host — that contract gap is decided when the fork UX is real (likely a return-type amendment)."

**The ruling this packet implements (lead, R27 — to be registered as D97 at review):** `saveForkToLibrary(): WorldMapData` — returns the fork's map as it stands (post-edits), detached from the library plane; the host persists it under whatever library id/name it chooses. The overlay is NOT in the return: the facade holds and mutates the CALLER'S overlay object (C24 reference doctrine — loadMap stores the caller's object), so after `forkMap()` re-points its `mapId`, the host already holds the chat-attached overlay.

**C24 (the detach mechanism):** the facade's internal state holds REFERENCES, never copies — the host may mutate the live map in place and `materialize()` propagates (the C24 hook). A fork therefore detaches by DEEP COPY: `forkMap()` replaces the facade's map reference with a deep copy under a NEW engine-assigned map id; from then on the host's mutations of the ORIGINAL library object propagate into nothing the facade holds. `forks never re-sync` is the deep copy, nothing more.

**C5 (ids):** "Ids belong to the engine. Callers never propose ids; rapid creations cannot collide." There is no map-id generator yet (the `wp-`/`we-` counters at facade.ts:783 are overlay-scoped). The new helpers generate map ids engine-side; uniqueness against the host's STORED maps is host knowledge the caller may pass as an exclusion set — the engine still generates, never accepts a proposed id.

**D79 (the new-map default):** "Fresh maps start at 1 px = 1 unit, distance-kind, label 'units' — geometric arcs price from the first stroke (C14 row 5) … One-time 'calibrate your scale' hint; calibration overwrites by explicit action only (C13/D44)."

**WorldMapData (src/core/api.ts — do NOT reorder or renumber existing fields):** `schemaVersion: 2; id: string; name: string; layers: LayerData[] (≥ 1); scale: { unitPerPx, unitLabel, unitKind, terrainMultipliers?, speed? }; nodes; edges; modes?`. The validator tolerates unknown extra keys (src/core/model/validate.ts:10 — forward compatibility), so an added optional field needs no migration (C30/C31).

**Facade current state (src/core/facade.ts):** `forkMap`/`saveForkToLibrary` are the explicit Phase 3 M4 stubs at lines 566-568 (`throw todo('Phase 3 M4', …)`). loadMap (lines ~515-560) is the template for every load-shaped saved-plane refresh: `state.map = validatedMap` (the reference, never a copy), `savedScale`, the A-014 id universes (`savedNodeIds`/`savedEdgeIds`/`savedLayerIds`), dirty cleared, viewer state reset. Read it before writing forkMap.
